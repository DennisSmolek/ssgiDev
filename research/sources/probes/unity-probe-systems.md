# Unity probe systems SSRT3 leans on (primer)

Only what's needed to understand the fallback in `ssrt3-fallback.md`. Two independent systems: Adaptive Probe Volumes (diffuse, SH) and Reflection Probes (specular-capable, cubemap).

## Adaptive Probe Volumes (APV)

- Manual (HDRP 17.0): https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@17.0/manual/probevolumes-concept.html
- Manual (generic/URP 6000.0): https://docs.unity3d.com/6000.0/Documentation/Manual/urp/probevolumes-concept.html
- Technical reference for the underlying SH data format: https://docs.unity3d.com/Manual/LightProbes-TechnicalInformation.html
- Code-level overview (third-party but accurate, cites the actual source tree): https://deepwiki.com/Unity-Technologies/Graphics/4.2-adaptive-probe-volumes

**What it is.** An APV is baked indirect lighting placed automatically by Unity as a 3D structure of "bricks," each brick a 4×4×4 grid of individual Light Probes ("HDRP automatically fills an Adaptive Probe Volume with a 3D structure of 'bricks'. Each brick contains 64 Light Probes, arranged in a 4 × 4 × 4 grid." — probevolumes-concept.html). Brick size (and thus probe spacing) adapts to local geometry density, with default spacings of 1, 3, 9, or 27 m — denser near complex geometry, sparser in open areas.

**What it stores.** Per probe: spherical-harmonic coefficients (the system supports progressive SH bands — `SphericalHarmonicsL1` = 4 coefficients (L0 + 3×L1), `SphericalHarmonicsL2` = 9 coefficients (L0 + 3×L1 + 5×L2) — selectable for quality/memory tradeoff), a validity flag (whether the probe sits in valid, non-geometry-intersecting space), and optionally baked sky-visibility/shading-direction data (`SkyOcclusionL0L1` textures) for a dynamic-sky-consistent look. Data is packed into GPU 3D texture arrays managed by a `ProbeBrickPool` (e.g. `_APVResL0_L1Rx`, `_APVResL1G_L1Ry`, `_APVResValidity`, plus a hierarchical brick-lookup index texture `_APVResIndex`), organized/subdivided by `ProbePlacement`/`ProbeSubdivisionContext`.

**How a shader queries it.** Include `Packages/com.unity.render-pipelines.core/Runtime/Lighting/ProbeVolume/ProbeVolume.hlsl` (also transitively available via HDRP's `Lighting.hlsl`, which SSRT3's compute shader already includes). "Each pixel of a GameObject samples lighting data from the eight closest Light Probes around it" — a per-pixel trilinear-ish blend across brick boundaries, not a single nearest probe or a baked-per-object constant (that older, coarser mode is "Light Probe Groups" in the Built-in pipeline: https://docs.unity3d.com/Manual/class-LightProbeProxyVolume.html). The actual call used by SSRT3 is `EvaluateAdaptiveProbeVolume(absoluteWorldPos, normalWS, backNormalWS, viewDirWS, screenPos, out bakeDiffuseLighting, out backBakeDiffuseLighting)` — it returns *already-convolved-with-the-normal* irradiance (a diffuse/Lambertian integral of the SH against the given direction), not raw SH coefficients — which is exactly why SSRT3 can plug an arbitrary fallback-sample direction in as the "normal" argument and get a meaningful directional irradiance value back.

**Legacy (non-adaptive) Light Probes** use the same SH-irradiance idea but simpler placement/interpolation (manual placement + tetrahedral interpolation between probes: https://docs.unity3d.com/Manual/LightProbes-TechnicalInformation.html). Data format: **27 floats per probe = 9 SH coefficients × 3 color channels**, third-order (L2) SH. Coefficient order: L0 (DC), L1 (y, z, x), L2 (xy, yz, zz, xz, xx−yy). Unity's shader reconstruction ("the method from Appendix A10 Shader/CPU code for Irradiance Environment Maps" in Peter-Pike Sloan's "Stupid Spherical Harmonics (SH) Tricks") lives in `UnityCG.cginc`. This is the same SH-irradiance math three.js's `getShIrradianceAt` implements (see `threejs-probe-options.md`) — same 9-coefficient L2 basis, same normalization constants family.

## Reflection Probes

- Manual: https://docs.unity3d.com/Manual/ReflectionProbes.html
- HDRP-specific manual (cubemap array atlas, planar variant): https://docs.unity3d.com/Packages/com.unity.render-pipelines.high-definition@14.0/manual/Reflection-Probe.html

**What it stores.** A **cubemap**: "a collection of six square textures that can represent the reflections in an environment ... conceptually like a box with flat images of the view from six directions ... painted on its interior surfaces," captured "by taking six 'snapshots' from a point in the scene." In HDRP this cubemap is baked with a full mip chain (roughness → mip, same idea as a PMREM) and packed into a shared `_ReflectionAtlas` (2D texture atlas) or `_EnvCubemapTextures` (cubemap array), depending on Unity version — SSRT3's `TraceReflectionProbes` has `#ifdef REFL_ATLAS_TEXEL_SIZE` branches for both.

**Placement & blending.** Each probe has "a zone of effect defined by an invisible box shape [or sphere] in the scene." When a shaded point falls in the overlap of several probes' influence volumes, "Unity can interpolate between them to allow for gradual changes in reflections." Mechanically (from the HDRP shader code SSRT3 reuses, `TraceReflectionProbes`/`FetchEnvLight`/`EvaluateLight_EnvIntersection`): the renderer maintains a **per-tile/cluster list of overlapping env lights** (same clustered/FPTL light-culling structure used for punctual lights — `GetCountAndStart(posInput, LIGHTCATEGORY_ENV, ...)`), and a shader loops that list, calling `EvaluateLight_EnvIntersection` per probe to parallax-correct the sample ray `R` against the probe's box/sphere influence shape and produce a blend `weight`, accumulating `weight * probeResult` until `totalWeight` saturates to 1 (`UpdateLightingHierarchyWeights`). This is a **local, position-dependent, parallax-corrected** cubemap lookup — the closest Unity analog to a "spatially-aware environment map," in contrast to a single global skybox/PMREM.

**Roughness → mip.** Reflection probes store a full mip chain; a rough BRDF lobe samples a higher (blurrier) mip. SSRT3's fallback path computes (but doesn't actually use) `MipLevelFromConeAngle(theta, cubemapSize)` from https://patapom.com/blog/BRDF/PreIntegration/ as the "correct" way to map an ambient sample's angular footprint to a mip level; the shipped code hardcodes `ambientMip = 3` instead.

## Why SSRT3 treats these as two exclusive options

APV gives cheap, purely-diffuse, position-varying irradiance (good match for the diffuse-only ambient term this fallback is filling in) but only exists/updates where baked (static scenes, or expensive-to-refresh dynamic GI). Reflection probes give a full directional radiance cubemap (can carry higher-frequency directional variation, and via `REFLECT_SKY` can degrade gracefully to the skybox outside any probe's influence) but are heavier per-sample (light-list loop) and are Unity's *specular* IBL mechanism repurposed here for ambient/diffuse duty. The paper's own future-work note (see `directional-ambient.md`) explicitly frames both as imperfect: "the common ambient light sources are either static (constant color, light probes) or expensive to update at runtime."
